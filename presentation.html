PROBLEM

연구 배경

LLM의 프로그래밍 언어 처리 능력은 아직 연구 진행 중이다.

  • 컴파일러는 동적 런타임 오류를 놓칠 수 있음 → 정적분석 도구 필요
  • 운영환경의 대량 코드는 사람이 직접 검사 불가
  • False Positive는 개발자의 도구 신뢰도를 떨어뜨림
소스코드를 해석·분석하는 것은 보안·성능 측면에서 중요. LLM의 능동적 정적분석 활용 가능성을 검증하고자 본 연구를 수행.
정적분석코드를 실행하지 않고 소스만 보고 결함·취약점을 찾는 분석 기법
LLMLarge Language Model. 대량 텍스트로 학습한 언어 이해·생성 모델
SonarQube대표적 오픈소스 정적분석 플랫폼. 룰 기반으로 품질·보안 이슈 검출
False Positive실제 문제가 없는데 결함으로 잘못 판정한 오탐. 신뢰도를 갉아먹는다

PIPELINE

SonarQube와 LLM의 파이프라인 차이

● SonarQube

  • Maven 빌드 먼저
  • 컴파일된 클래스 파일 분석
  • qualityGate.status ≠ OK → 중단

● GPT-4 (LLM)

  • 빌드 전에 작동
  • 원본 .java 파일 직접 분석
  • 하나라도 F → 파이프라인 중단

WHY ACCURATE

정확도 차이의 원인

GPT의 언어 맥락 이해 능력 때문으로 판단

  • GPT는 토큰화·유사도 계산으로 소스코드의 맥락까지 이해
  • 해당 코드 자체뿐 아니라 주변 코드·전반적 흐름까지 파악
  • SonarQube: 규칙 기반으로 한정된 영역만 분석
  • GPT: 폭 넓은 관점에서 코드 이해·분석
LLM은 분석 시간은 오래 걸렸지만 완벽에 가까운 정탐률을 보여 별도 튜닝 없이도 활용 가능한 것으로 판단.
룰 기반사전 정의된 규칙(패턴)에 일치하면 결함으로 보고하는 분석 방식
토큰화텍스트·코드를 모델이 처리할 수 있는 최소 단위(토큰)로 쪼개는 과정
맥락 추론단일 라인이 아닌 주변 코드와 흐름을 종합해 의미를 판단하는 능력

WHY SLOW

속도 차이의 원인

  • SonarQube: 사전 정의된 규칙 기반 점검 → 빠름
  • LLM: 코드 전체 토큰화 + 맥락 추론 → 느림
운영 환경의 신속한 배포를 위해 정적분석 범위와 속도의 적절한 균형이 필요.
규칙 기반사전 정의된 규칙(패턴)에 일치하면 결함으로 보고하는 분석 방식
토큰LLM이 처리하는 최소 단위. 길이·요금·지연이 토큰 수에 비례

CONCLUSION

결론

  • 기존 CI/CD에 LLM 호출 스크립트만 추가해 통합 가능
  • 맥락 추론으로 규칙으로 정의하지 못한 사항까지 점검
  • 여러 도구 조합 없이 LLM 하나로 포괄적 점검 가능
  • 운영 환경에서는 속도-범위의 균형 필요
  • 자체 LLM 인프라 → 특화 모델로 시간 단축
  • 그렇지 않으면 사후점검 형태로 활용 가능
규칙 기반 분석이 탐지하지 못하는 부분을 LLM이 효과적으로 보완해줄 것으로 기대.
